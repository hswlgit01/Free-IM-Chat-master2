根因 · 最重要的一条

索引在代码里有，在数据库里没有

createDatabaseIndex() 整个函数体被注释掉了

崩到这个程度，账依然是对的

对全部 9 个压测红包跑一致性校验：无超发、无重复领取、remaining_count 与实际领取数全部吻合。Redis 预留 + Lua 原子操作 + (transaction_id, user_id) 唯一索引这套幂等设计是站得住的。

事故 · 压测中暴露的两个独立缺陷

顺带发现的问题

已导致测试环境 MongoDB 宕机

OpenIM 的服务日志写在没人看得见的地方，一轮压测 23.7GB

log.yml 里 storageLocation: ./logs/ 是相对路径，而服务进程的工作目录是二进制所在目录，所以日志实际落在 /im-server/_output/bin/platforms/linux/amd64/logs/——既不是挂载出来的 /data/logs/server，宿主机上也看不到。叠加 remainLogLevel: 6（debug）和一天才轮转一次，首轮压测写了 23.7GB 把根分区打满，mongod 分配不出 WiredTiger journal 直接 panic 退出，进入重启循环。

已清理并恢复，副本集 PRIMARY 正常、数据完好。压测工具现已内置磁盘看门狗。这个隐患在生产环境同样存在，且和红包无关——任何一个高消息量的日子都可能触发。

组织缓存命中后，AES 密钥变成空串

组织缓存 GetCache 用 json.Marshal 序列化，而 Organization.AesKeyBase64 的标签是 json:"-"。缓存未命中时从库里读，密钥正常；一旦缓存命中，反序列化出来的密钥就是空串，嵌入式登录随即报 crypto/aes: invalid key size 0。表现为「登录时好时坏」——缓存过期后第一次成功，之后全部失败。

P1-1：toPush 整批一条消息

msgtransfer 的 batcher 本来就把消息按会话攒成批（默认 1000 条一批），但 toPushTopic 又对每条单独 produce 一次，等于白攒。现在整批发一条，下游 push 消费端也就只需解一次包、取一次群成员。

为了不重新生成 protobuf，批量信封复用了已有的 MsgDataToMongoByMQ（它本来就是 {conversationID, repeated msgData}）。消费端能可靠区分新旧格式：旧格式的字段 1 是 msgData（length-delimited），按批量格式解析时与 lastSeq（varint）线型冲突必然报错。网关下发仍是每条一次——msggateway 的接口本身按单条消息定义，合并它要改网关协议，属于 P2 范围。

msgtransfer/online_history_msg_handler.go · push/push_handler.go handleBatch

P1-2：已读 seq 改 BulkWrite

SetHasReadSeqToDB 原来 for 循环逐用户写，而 Mongo 侧每个用户又是「1 次读 + 1 次 upsert」——一批 1000 条不同发送者的消息就是 2000 次串行往返。现在一次 BulkWrite 写完，并用 $max 让「只前进不后退」由 MongoDB 原子完成，顺带修掉了原来「读-比-写」之间的竞态。

controller/msg_transfer.go · mgo/seq_user.go SetUserReadSeqBatch

2000 并发这一档，瓶颈又换了一个

红包侧现在报的是 Lua脚本执行失败: context deadline exceeded（606 个）和抢分布式锁失败（247 个）——压力转到了 Redis 的槽位预留上。但这一档要谨慎解读：4 核机器上同时跑着 2000 个压测协程和全部被测服务，测的已经是这台机器而不是这套软件。

怎么再跑一遍

  1. 开压测开关 — 在测试服执行 /root/stress-backup/recreate-chat.sh on，用完全相同的镜像和挂载重建 chat 容器，只多加 STRESS_TEST_RECEIVE=1。跑完用 off 还原。
  2. 造数据 — ./rpbench prepare -receivers 5000，产出 plan.json。每轮压测复用同一份计划，前后对比才成立。
  3. 采指标 — ./rpbench monitor -tag <标签> 后台跑，注意要和压测窗口对齐（第一次就因为监控先结束而白采了一轮）。
  4. 打压力 — ./rpbench bench -tag <标签> -c 300 -count 200 -amount 200。
  5. 校验一致性 — ./rpbench verify 检查超发、重复领取、计数对不对得上。性能优化不能把账算错，每轮都要跑。

这些数字的边界

测试机只有 4 核，且压测器和被测服务跑在同一台机器上。绝对值不能直接套到生产环境——4~5 req/s 是这台机器的数字。有意义的是形状（吞吐不随并发增长）和比例（每次抢包 8 次数据库操作），这两点与机器规格无关。

CPU 列存在采样错位。docker stats --no-stream 和 kafka-consumer-groups.sh 都是秒级慢调用，实际采样间隔被拉长到 9~15 秒，个别行的 CPU 值和同行的计数器不同步。CPU 只用来看量级，不要读瞬时值。

压测走的是 receive_stress 接口，它会跳过群成员校验。也就是说 P0-6 那条（每次抢包拉全量群成员）的开销没有体现在上面的数字里——真实线上路径比测出来的还要重。

CountByTransactionID 没有出现在查询日志里。按代码它应该每次抢包都执行，但日志中没有对应的 COUNT 记录，可能是这个 DAO 方法没被查询日志埋点覆盖。P0-5 的收益尚未被实测证实，属于读码推断。
